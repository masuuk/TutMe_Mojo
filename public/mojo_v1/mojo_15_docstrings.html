Chapter 15

📝 Docstrings

Mojo turns documentation into data: docstring literals feed the API reference generator, and the compiler itself validates their structure — placement, sections, entries, and summary sentences.

1. Placement

Mojo uses docstring literals to generate API reference documentation. Place them immediately after declarations:

def greet(name: String) -> String:
    """Returns a greeting string for the given name.

    Produces a simple `"Hello, name!"` string suitable for display
    or logging.

    Args:
        name: The name to include in the greeting.

    Returns:
        A greeting of the form `"Hello, name!"`.
    """
    return "Hello, " + name + "!"
DeclarationPosition
Function or methodAfter the signature, before the body
Struct or traitAfter the opening line, before members
Field or comptimeAfter the declaration, not before it
Module or packageFirst string in the file, after imports

Type, trait, and function docstrings sit at the same indentation as the declaration; field and comptime docstrings match the name's indentation:

struct Color:
    """Represents an RGB color."""          # Struct docstring

    var r: UInt8
    """The red channel, in [0, 255]."""      # Field docstring

    comptime MAX: UInt8 = 255
    """The maximum value for any channel."""  # comptime docstring

    def to_hex(self) -> String:
        """Converts the color to a hex string.""" # Method docstring
        ...

Module docstrings go as the first string in the file; package docstrings live in __init__.mojo. Mojo docstrings follow Python docstring conventions and the Google docstring style guide.

The summary line

A docstring's first sentence is its summary — it appears in index views and search results. Separate it from the body with a blank line. Start with a capital letter, avoid repeating the declaration name, and end with a period (the compiler also accepts !, ?, or a closing backtick):

  • Functions/methods: present-tense verb — "Clamps a value to the range [low, high]."
  • Structs/traits: noun phrase — "A fixed-capacity circular buffer."
  • Fields/comptime: noun phrase — "The red channel, in [0, 255]."

2. Labeled Sections

Structured sections use a labeled header followed by indented name: Description. entries. The doc generator includes type information automatically, so don't repeat it in descriptions. Four labels are compiler-validated against the declaration:

LabelDocuments
Parameters:Compile-time parameters
Args:Runtime arguments
Returns:Return values
Raises:Error conditions
 
def resize[dtype: DType](
    data: List[Scalar[dtype]],
    size: Int,
    fill: Scalar[dtype] = 0,
) raises -> List[Scalar[dtype]]:
    """Resizes a list by truncating it or padding it with a fill value.

    Parameters:
        dtype: The element type of the list.

    Args:
        data: The source list to resize.
        size: The target length.
        fill: The value used to pad the list when growing it.

    Returns:
        A new list with length `size`.

    Raises:
        An error if `size` is less than or equal to zero.
    """
    ...

Mojo doesn't define a canonical label set — any Label: starts a new section — but the conventions are strong. Note Mojo uses Args, not "Arguments".

Parameters and Constraints

Use Parameters: when a compile-time parameter's role or requirements aren't obvious. Simple per-parameter requirements can be inline Constraints: clauses; requirements spanning multiple parameters or the target architecture get a standalone section:

def dot[size: Int](
    a: SIMD[DType.float32, size],
    b: SIMD[DType.float32, size],
) -> Float32:
    """Computes the dot product of two SIMD vectors.

    Constraints:
        - `size` must be a power of two.
        - The target must support AVX2 or NEON.
    """
    ...

Examples

Examples: is not compiler-checked but is a core convention — normally the last section, with example code left-aligned to the label in fenced ```mojo blocks:

"""...

Examples:

```mojo
var names = ["alice", "bob", "carol"]
print(names.find("bob").value())  # 1
print(names.find("dave") is None) # True
```
"""

3. Custom Labels

Beyond the validated four, these recommended labels cover the rest of an API's contract:

LabelDocuments
Preconditions:Runtime conditions the caller must satisfy
Performance:Complexity, allocation, vectorization, latency costs
Safety:Requirements whose violation causes undefined behavior
See:Related APIs, standards, algorithms, references

Choose among the three "condition" labels by how the condition is enforced:

  • Preconditions: — a runtime condition that aborts execution when violated and can't be caught (e.g. a runtime assertion).
  • Constraints: — a compile-time requirement that fails compilation when violated.
  • Raises: — a runtime condition that raises a catchable error.

Other labels (like Notes:) are accepted, but prefer putting that content in the docstring body. A consistent section order helps scanning — the recommended order is:

Parameters: → Args: → Returns: → Raises: → Preconditions: → Constraints: → Safety: → Performance: → See: → Examples:

Inline formatting

Docstrings support Markdown, inline code formatting, escape sequences, KaTeX math, and HTML tags. Double KaTeX backslashes (\\frac, \\cdot); $$ is ignored inside backticks and fenced code blocks. String escape sequences are honored everywhere — \n produces a newline even inside example code blocks, while \\t renders as the two characters \t.

4. Hidden Elements

@doc_hidden

The @doc_hidden decorator excludes a declaration from generated documentation. It still compiles normally — there's just no doc output. Common uses: hiding dunder lifecycle methods, private helpers, and deprecated internals kept for compatibility.

@doc_hidden
def _internal_helper(data: UnsafePointer[UInt8]) -> Int:
    pass

Hidden example lines

Prefix a line in an example with %# to hide it from generated docs while keeping it visible in source. Uses include hiding setup code and expected-output lines:

"""...
%# var result = format_result(0.857)
%# print(result)  # 85.7%
..."""

5. Compiler Checks

Mojo validates docstrings during compilation and reports common issues:

$ mojo optionalref.mojo
optionalref.mojo:5:8: warning: doc string summary should begin with a
capital letter or non-alpha character, but this begins with 'a'
"""an error type for when an empty `OptionalRef` is accessed"""
        ^

Validation modes

Two modes apply, in both mojo and mojo doc:

  • Strict — for public APIs (declarations that don't start with _, aren't @doc_hidden, aren't synthesized, and sit at module scope or in a public struct/trait). Summary sentences and section body text must begin with a capital letter or non-alpha character and end with ., !, ?, or a backtick.
  • Normal — for private and internal declarations.

Universal checks (always on): section structure (overindented labels, duplicate sections, empty sections); Args:/Parameters: entries (names a missing argument, duplicates, out-of-declaration-order entries, missing descriptions, missing documented arguments); and consistency (Returns: on a function without a return value, Raises: on a non-raising function).

Strict mode with --diagnose-missing-doc-strings is the CI-grade setting. It flags missing docstrings on public functions, structs, traits, fields, comptime declarations, and modules; missing required sections (Args: when the function has arguments, Parameters: when it has required parameters, Returns:, Raises:); and more. Constraints: and custom labels are not checked:

$ mojo doc --diagnose-missing-doc-strings -Werror -o /dev/null stdlib/std/
optionalref.mojo:1:1: warning: public module 'OptionalRef' is missing a doc string
optionalref.mojo:2:8: warning: struct takes parameters, but has no
'Parameters' in doc string
🚀 Pro Tip:

Run mojo doc --diagnose-missing-doc-strings locally before publishing a package — it's the same gate the standard library uses with -Werror.

📋 Summary:

Docstrings in Mojo are a checked contract, not comments: the compiler validates placement, sections, and entries; mojo doc turns them into reference pages and can enforce their very existence. Write them as you write the code — the summary sentence, the labeled sections, and the examples are all part of the API.
