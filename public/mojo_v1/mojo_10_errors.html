Chapter 10

Errors & Context Managers

Raise, handle, and type your failures — then manage resources safely with with.

1. Errors as Values

Mojo represents errors as values — specifically, as alternate return values from functions. Unlike the stack-unwinding exceptions of C++ or Java, Mojo errors don't unwind the call stack, so their runtime overhead is as low as returning and checking an extra Bool. This design even enables error handling where traditional exceptions can't exist: GPU kernels.

An error interrupts normal execution. If a handler exists in the current function, it resumes there; otherwise the error propagates to the caller, and so on. If nothing catches it, the program terminates with a non-zero exit code and prints:

Unhandled exception caught during execution: record not found

2. Raising Errors

The built-in Error type carries a text message and is the right default for application code. Declare that a function may fail with the raises keyword; raise with the constructor or the string-literal shorthand (the compiler wraps it in an Error):

def read_file(path: String) raises -> String:
    if not path:
        raise "path cannot be empty"
    return "contents of " + path

# These two raises are equivalent:
#   raise Error("file not found")
#   raise "file not found"

def main() raises:
    print(read_file("data.txt"))
contents of data.txt

Mojo functions are non-raising by default. A non-raising function that calls a raising one must either handle the error locally or declare raises itself — otherwise the program won't compile.

3. Handling Errors: try / except / else / finally

ClauseRuns when…
tryAlways first — contains the code that might raise
except eThe try block raised — e binds the error value (max one per try)
elseNo error occurred — skipped if try exits via continue/break/return
finallyAlways, after everything else — even if a clause exits or re-raises

You must include except or finally (or both); else is optional:

def process_record(id: Int) raises -> String:
    if id > 999:
        raise Error("record not found")
    return String("record_", id)

def main() raises:
    try:
        var result = process_record(1001)
    except e:
        print("handled:", e)
    else:
        print("success:", result)
    finally:
        print("cleanup always runs")
handled: record not found
cleanup always runs

Re-raising

Pass a caught error back to raise to propagate it after logging. Re-raising copies the error — cheap, since its message and optional stack trace are reference-counted. To skip the copy, transfer ownership with the sigil: raise e^. Custom error types that aren't ImplicitlyCopyable require the transfer sigil.

📌 Tip:

Use finally for cleanup that must happen regardless of outcome — file handles, locks, connections. Or better: let a context manager do it for you (Section 9).

4. Typed Errors

When callers need structured data — an error code, a field name — define a custom error type. Any struct can serve as an error type; no base class or trait required. Implementing Writable is recommended so the error prints readably:

@fieldwise_init
struct ValidationError(Copyable, Writable):
    var field: String
    var reason: String

    def write_to(self, mut writer: Some[Writer]):
        writer.write("ValidationError(", self.field, "): ", self.reason)

def validate_username(username: String) raises ValidationError -> String:
    if username.byte_length() == 0:
        raise ValidationError(field="username", reason="cannot be empty")
    return username
try:
    var name = validate_username("")
except e:
    # e is a ValidationError — fields accessed directly, no casting:
    print("Error in field '" + e.field + "': " + e.reason)

# Output: Error in field 'username': cannot be empty
  • One error type per function. Every raise in the body must match the declared type or compilation fails.
  • The type is inferred at the catch site. There is no except ErrorType as e: syntax — the compiler deduces the type from the function being called.
  • Different types need separate try blocks (see Section 7).
  • If the type conforms to Writable, pass it straight to print(e).
💡 Key Insight:

Typed errors work on GPUs and embedded targets too — as long as you avoid heap-allocated fields like String. That's the real payoff of representing errors as values instead of stack unwinding.

5. Multiple Error Conditions

A function declares only one error type, so multiple failure modes must live inside that one type. Mojo offers two patterns:

Option A: Enumerated error type

A single struct with an integer variant field and comptime constants — simplest when you only need to distinguish conditions. With Equatable, == is auto-synthesized for comparing variants:

@fieldwise_init
struct FileError(Equatable, ImplicitlyCopyable, Writable):
    var _variant: Int

    comptime not_found = FileError(_variant=1)
    comptime permission_denied = FileError(_variant=2)
    comptime already_exists = FileError(_variant=3)

    # ...variant_name()/write_to() produce readable messages...

def open_file(path: String) raises FileError -> String:
    if not path:
        raise FileError.not_found
    if path == "/secret":
        raise FileError.permission_denied
    return "Contents of " + path
try:
    print(open_file("/secret"))
except e:
    if e == FileError.not_found:
        print("Not found:", e)
    elif e == FileError.permission_denied:
        print("Permission denied:", e)

Option B: Variant of error structs

When each condition carries different data, give each its own struct and combine them with the stdlib Variant:

from std.utils import Variant

# @fieldwise_init structs NotFoundError(path)
#   and PermissionError(path, required_role) defined here...

comptime FileError = Variant[NotFoundError, PermissionError]

def open_file(path: String) raises FileError -> String:
    if not path:
        raise FileError(NotFoundError(path))
    if path == "/secret":
        raise FileError(PermissionError(path, "admin"))
    return "Contents of " + path

try:
    print(open_file("/secret"))
except e:
    if e.isa[PermissionError]():
        print("Access denied:", e[PermissionError])
Access denied: permission denied on /secret (requires admin)

e.isa[T]() tests which struct is active; e[T] extracts it with full type information. Rule of thumb: enumerated type when you only distinguish conditions; Variant when each needs its own fields.

6. The Never Type & Parametric Raises

Never has no constructors — it can't be instantiated — which lets it express two opposite guarantees in error signatures:

  • raises YourError -> Never — the function always raises, never returns.
  • raises Never -> T — the function never raises; equivalent to omitting raises.
# Always raises, never returns:
def panic(msg: String) raises -> Never:
    raise Error(msg)

def get_value_or_panic(maybe: Optional[Int]) raises -> Int:
    if maybe:
        return maybe.value()
    panic("value is missing")   # Never substitutes for Int here
# Because Never can stand in for any type, a call to panic()
# satisfies the "must return Int" requirement of this branch —
# the compiler knows that line never completes normally.

Parametric raises

Generic wrappers can propagate whatever error type their function argument carries. The error type is just another compile-time parameter, inferred at the call site:

def run_action[
    ErrorType: AnyType
](action: def() thin raises ErrorType -> Int) raises ErrorType -> Int:
    return action()

# fetch_data() raises NetworkError → run_action raises NetworkError
# parse_config() raises ParseError  → run_action raises ParseError

# A non-raising argument infers Never — run_action becomes
# non-raising, and no try block is needed:
var result = run_action(get_value)
print("Got value:", result)
Got value: 99

The thin marker appears because action is a noncapturing function value (Chapter 8's thin lambdas).

7. Mixing Error and Typed Errors

Real codebases mix plain Error-raising functions with typed ones. Three rules keep them composable:

Wrap Error at API boundaries

def validate_with_error(value: Int) raises -> Int:
    if value < 0:
        raise "value cannot be negative"
    return value

def wrapped_validate(value: Int) raises ValidationError -> Int:
    try:
        return validate_with_error(value)
    except e:
        raise ValidationError(field="value", reason=String(e))

Avoid bare raises with typed errors

A bare raises on a function that calls typed-error code causes type erasure: the runtime preserves the original error's identity and message, but the compiler only sees Error — so callers lose field access. Always write raises YourErrorType. (Catching locally still gives full field access; erasure only affects errors that propagate through.)

Never mix types in one try block

Calling an Error-raising function and a typed-raising function in the same try won't compile:

error: cannot call function that may raise 'Error' in a context that
supports an error type of 'ValidationError'

Use separate try blocks per type, or wrap as shown above.

8. Stack Traces

Because errors are return values rather than unwinding exceptions, stack trace collection isn't automatic — it needs heap allocation and runtime overhead, so it's off by default. Two steps turn it on:

  1. Compile with debug symbols: mojo build --debug-level full app.mojo (or -g).
  2. Run with the environment variable set: MODULAR_DEBUG=stack-trace-on-error ./app.

With both, an unhandled error prints the full call chain with source locations: main() → func1() → func2() → Error.__init__(). Note that running via mojo run/mojo doesn't symbolicate traces even with --debug-level full — build and run the binary.

You can also capture the trace programmatically. Bind the error in except e: and call its method — it returns Optional[String], which is None when collection was disabled:

def main() raises:
    try:
        func1()
    except e:
        print(e)
        var stack_trace = e.get_stack_trace()
        if stack_trace:
            print(stack_trace.value())
        else:
            print("No stack trace available")
Intentional error
--------------------
#2 0x... Error.__init__[...](...) .../builtin/error.mojo:159:38
#3 0x... app::func2() app.mojo:14:16
#4 0x... app::func1() app.mojo:18:10
#5 0x... app::main() app.mojo:23:14
⚠️ Watch Out:

Stack traces are a feature of the built-in Error type only. Typed errors don't capture them — the trace is collected inside Error.__init__(), and custom structs have no equivalent hook.

9. Context Managers & with

A context manager allocates a resource and guarantees its release at the end of a block — even if an error occurs. The naive pattern is fragile:

# If f.read() raises, close() never runs:
# buffered writes are lost, handles leak.
var f = open(input_file, "r")
var content = f.read()
f.close()

# try/finally fixes it, verbosely:
var g = open(input_file, "r")
try:
    var content = g.read()
finally:
    g.close()
# FileHandle is a context manager — close() is automatic:
with open(input_file, "r") as f:
    var content = f.read()

# Multiple managers in one statement:
with open(input_file, "r") as f_in, open(output_file, "w") as f_out:
    var output_text = f_in.read().upper()
    f_out.write(output_text)

The with statement works transparently with both error styles. Other stdlib context managers include NamedTemporaryFile, TemporaryDirectory, BlockingScopedLock, and assert_raises.

Writing your own

A struct becomes a context manager by implementing __enter__() (initialize state, return the manager) and __exit__() (release resources; runs even on continue/break/return/raise):

import std.time

@fieldwise_init
struct Timer(ImplicitlyCopyable):
    var start_time: Int

    def __enter__(mut self) -> Self:
        self.start_time = Int(time.perf_counter_ns())
        return self

    def __exit__(mut self):
        var elapsed_ms = round(
            Float64(time.perf_counter_ns() - self.start_time) / 1e6, 3
        )
        print("Elapsed time:", elapsed_ms, "milliseconds")

def main() raises:
    with Timer():
        print("Beginning execution")
        time.sleep(1.0)
        print("Ending execution")
Beginning execution
Ending execution
Elapsed time: 2010.0 milliseconds

Error-aware exits

An overloaded exit receives the error and decides what happens — return True to suppress, False to re-raise, or raise something new:

OverloadHandles
def __exit__(mut self)All completions without distinguishing errors
def __exit__(mut self, e: Error) raises -> BoolRuns instead when an Error occurred in the block
def __exit__[ErrType: AnyType](self, err: ErrType) -> BoolTyped errors — full type preserved; inspect with reflect[ErrType] / conforms_to
📌 Tip:

If your manager has nothing to release, you can omit __exit__() entirely — the object is simply destroyed when the block ends.

10. Chapter Summary

  • Errors are values — alternate return values with near-zero overhead, usable even on GPUs.
  • Raise with raise "message" (shorthand for Error) or a typed value; declare failure modes in the signature with raises.
  • Handle with try/except e/else/finally; re-raise cheaply, transfer with raise e^.
  • Typed errors are plain structs carrying structured data; one type per function, inferred automatically at the catch site.
  • Multiple conditions: enumerated variant structs, or Variant[...] when each condition carries different fields.
  • Never marks always-raising functions; raises Never proves a function can't fail; parametric raises propagate error types through generics.
  • Keep types sharp: wrap Error at boundaries, never use bare raises over typed code, one error type per try block.
  • Stack traces: opt-in via MODULAR_DEBUG=stack-trace-on-error + -g; Error-only.
  • Context managers make cleanup automatic: __enter__/__exit__, optional error-aware overloads that can suppress or transform failures.
