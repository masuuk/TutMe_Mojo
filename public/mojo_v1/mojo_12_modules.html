Chapter 12

Modules, Packages & Toolchain

Organize code into importable modules and packages, drive the compiler with the mojo CLI, target CPUs and GPUs — and gate features at compile time.

1. Mojo Modules

A module is a single Mojo source file whose code is meant for use by other files that import it. Modules typically contain APIs — not an entry point. Notice this one has no main(), so you can't execute it directly:

struct MyPair:
    var first: Int
    var second: Int

    def __init__(out self, first: Int, second: Int):
        self.first = first
        self.second = second

    def dump(self):
        print(self.first, self.second)
# Import one member:
from mymodule import MyPair
var mine = MyPair(2, 4)

# Import the whole module:
import mymodule
var mine = mymodule.MyPair(2, 4)

# Alias the module:
import mymodule as my
var mine = my.MyPair(2, 4)
$ mojo main.mojo
2 4

These imports work when mymodule.mojo sits in the same directory as main.mojo. Currently you can't import .mojo files from other directories as bare modules — that requires a package, next.

📌 Tip:

A module may include a main() and be executable, but that's not the practice — modules exist to be imported by programs that have their own entry point.

2. Mojo Packages

A package is a directory of modules that includes an __init__.mojo file. That file is essential — without it, Mojo won't recognize the directory as a package and you can't import its modules:

project
├── main.mojo
└── mypackage/
    ├── __init__.mojo   ← required (can be empty)
    └── mymodule.mojo
from mypackage.mymodule import MyPair

def main():
    var mine = MyPair(2, 4)
    mine.dump()
$ mojo main.mojo
2 4

With the package in place, directory-based imports work from anywhere in your project — the same-directory restriction applies only to bare modules.

3. The __init__ File

Unlike Python, Mojo has no top-level code in source files — so __init__.mojo can't execute statements on import. It can, however, hold structs and functions, and more idiomatically, re-export module members so they're importable straight from the package name:

# mypackage/__init__.mojo — this one line is the whole file:
from .mymodule import MyPair
# Before: full dotted path required
from mypackage.mymodule import MyPair

# After: the package re-exports it
from mypackage import MyPair

This is exactly how the accelerator library works. The functional module lives in max.algorithm — moved out of the standard library in Mojo 1.x / MAX 26.5, when GPU and algorithm APIs migrated to the max package — so both of these import its map() — the second works because algorithm/__init__.mojo re-exports its submodules:

from max.algorithm.functional import map   # module path
from max.algorithm import map                      # package scope

Which package modules are re-exported to package scope varies and may change — check each module's docs for its importable members.

4. Precompiled Packages (.mojoc)

You can compile a package into a single precompiled file that loads faster as a dependency to another Mojo compile:

# Compile the package to a .mojoc file:
$ mojo precompile mypackage -o mypack.mojoc

# Project can now ship source elsewhere; layout becomes:
project
├── main.mojo
└── mypack.mojoc

# The .mojoc filename becomes the package name, so:
from mypack.mymodule import MyPair
  • A .mojoc contains non-elaborated code, shareable across systems; it becomes an architecture-specific executable only after import into a program compiled with mojo build.
  • It is tied to the exact compiler version that produced it — loading one into a different compiler version fails. It's not a generic distributable format.
  • To rename a package you can't just rename the file — the name is encoded inside. Run mojo precompile again with a new name.

Escaped identifiers

Package names come from directory names (source) or the .mojoc filename (binary). When a name isn't a valid identifier, escape it in backticks and alias it:

import `модул`
import `package-with-hyphens and a space!` as package_without_hyphens_or_a_space

def main():
    `модул`.`здрасти`()
    package_without_hyphens_or_a_space.hello()

6. Compilation Targets

Targets describe where and how your program runs: platform, CPU, features, and optional accelerators — for native builds and cross-compilation alike. Start by asking the compiler what it sees and supports:

mojo build --print-effective-target    # your host config
mojo build --print-supported-targets    # architectures: arm64, aarch64, amdgcn...
mojo build --print-supported-cpus --target-triple=aarch64-apple-macosx
mojo build --print-supported-accelerators
# Sample on an Apple M4 MacBook Pro:
Effective target configuration:
  --target-triple arm64-apple-darwin25.3.0
  --target-cpu apple-m4
  --target-features +aes,+bf16,+complxnum,+crc,+dotprod,...
  --target-accelerator metal:4
NVIDIA (CUDA):   sm_52 Maxwell ... sm_90 Hopper (H100) ...
AMD (ROCm/HIP):  gfx942 CDNA3 (MI300X) ...
Apple Silicon:   apple-m1 ... apple-m2 ...
Other:           cuda (Generic CUDA)

Target triples

A target triple identifies the platform — architecture, vendor, OS — and is the starting point for cross-compilation:

# x86_64-unknown-linux-gnu / aarch64-apple-macosx

mojo build --target-triple aarch64-unknown-linux-gnu \
    --target-cpu cortex-a72 \
    --emit object -o myapp.o myapp.mojo

mojo build --target-triple x86_64-unknown-linux-gnu \
    --target-cpu x86-64-v3 \
    --target-features "+avx512f" \
    --emit object -o myapp.o myapp.mojo

# Flags: --target-triple  platform (arch + vendor + OS)
#        --target-cpu      specific processor model
#        --target-features individual feature toggles
#        --target-accelerator  GPU or accelerator arch
# Same hardware, GCC/Clang conventions:
mojo build --target-triple x86_64-unknown-linux-gnu \
    --mcpu=haswell \
    --emit object -o myapp.o myapp.mojo

# --march  instructions allowed (e.g. x86-64-v3+avx512f)
# --mcpu   architecture + tuning from one CPU name
# --mtune  tuning only; code still runs on other CPUs

mojo build --target-triple x86_64-unknown-linux-gnu \
    --march=x86-64 --mcpu=haswell --mtune=skylake \
    --emit object -o myapp.o myapp.mojo
⚠️ Watch Out:

Never mix the two families in one command — --target-cpu with --march/--mcpu is an error. Also, when cross-compiling to a different architecture with Mojo flags, set --target-cpu alongside --target-triple: the CPU defaults to your host processor, which may be invalid for the target (unknown target CPU 'apple-m4').

Accelerators & emit options

Heterogeneous builds generate host code plus GPU device code in one build. --emit asm on a GPU target produces per-kernel sidecars: .ptx (NVIDIA), .amdgcn (AMD), .ll (Metal):

mojo build --target-accelerator=nvidia:sm_90 myapp.mojo   # H100
mojo build --target-accelerator=amdgpu:gfx942 myapp.mojo  # MI300X
exe (default)   Executable binary      Native only
shared-lib      Shared library         Native only
object          Object file (experimental)  Cross OK
llvm            Unoptimized LLVM IR    Cross OK
llvm-bitcode    LLVM IR bitcode        Cross OK
asm             Assembly + GPU sidecars   Cross OK
⚠️ Cross-compilation is in progress:

Object, assembly, and IR outputs work for any supported target, but producing a fully linked cross-compiled executable requires an external linker for the platform — --emit exe/shared-lib fail at the link step when cross-compiling. Cross-compiled binaries also don't bundle external libraries (Python, C, Modular runtime) — the target environment must provide them.

7. Compile-Time Defines

The -D flag passes key-value pairs from the command line into Mojo code — Mojo's answer to C's preprocessor, except values are first-class compile-time parameters in the type system, not string substitutions:

# -Dkey=value or -D key=value — joined with "=":
mojo run -Dmode=release -Dverbose -Dmax_threads=8 hello.mojo

# -D KEY=VALUE   parsed per get_defined_*[]() reader
# -D KEY         flag with no value; is_defined["K"]() is True
# -D KEY=42      read with get_defined_int["K"]()
from std.sys import get_defined_string

def main():
    comptime mode = get_defined_string["mode", "debug"]()

    comptime if mode == "release":
        print("optimized path")
    else:
        print("debug path with extra checks")
$ mojo run -Dmode=release hello.mojo
optimized path

All define names are compile-time StaticString parameters, read through std.sys:

ReaderReturnsOn missing define
is_defined["verbose"]()Bool — presence only (like #ifdef), value ignoredFalse, never errors
get_defined_bool["verbose"]()Bool — 1/true/True/on are truthy; yes is notdefault False
get_defined_int["max_threads"]()Int — base-10 only (0x10, 1_000 fail)Compile error (defaulted version available)
get_defined_string["mode"]()StaticStringCompile error (defaulted version available)
get_defined_dtype["dtype", DType.bfloat16]()DType — default required; canonical names (float16, not fp16)Returns default
⚠️ Watch Out:

get_defined_bool errors when the define exists but has no value (-D verbose), and avoid default=True — it inverts the meaning confusingly. If "on unless explicitly off" is the intent, is_defined[]() states it more clearly.

8. Platform & Architecture Detection

std.sys.info exposes parameter-evaluable functions for branching on the compilation target (what the compiler builds for — set the target flags from Section 6 to aim elsewhere):

from std.sys import CompilationTarget

def compute():
    comptime if CompilationTarget.has_avx512f():
        print("AVX-512 path")
    elif CompilationTarget.is_apple_silicon():
        print("Apple Silicon path")
    else:
        print("generic path")
Apple Silicon path
QuestionAPI
Which OS?CompilationTarget.is_linux(), is_macos() — no Windows targets natively
Which CPU family?CompilationTarget.is_x86(), is_apple_silicon(), is_apple_m1() … is_apple_m5()
Which instruction sets?CompilationTarget.has_avx512f(), has_neon(), …
Am I compiling for a GPU?is_nvidia_gpu(), is_amd_gpu(), is_apple_gpu(), is_gpu()
Does the host have an accelerator?has_accelerator(), has_nvidia_gpu_accelerator(), …

The distinction matters: is_nvidia_gpu() asks "am I compiling for an NVIDIA GPU?" while has_nvidia_gpu_accelerator() asks whether such acceleration is available — which can also be true when the target is the GPU itself.

📌 Tip:

Combine detection with comptime assert (Chapter 8) to hard-block misuse: comptime assert is_gpu(), "this function requires a GPU target" prints a constraint failed note at the call site in a CPU build.

9. Debug & Optimization Gating

Debug and optimization features are independent — enabling one doesn't enable another. "Debug build" can mean several different things in Mojo:

GoalFlagEffect
Full debug info (LLDB symbols)-g / --debug-level=fullSets __DEBUG_LEVEL="full"
Line tables only-g1 / --debug-level=line-tablesSets __DEBUG_LEVEL="line-tables"
Disable optimization-O0 / --no-optimizationSets __OPTIMIZATION_LEVEL=0
AddressSanitizer--sanitize=addressSets __SANITIZE_ADDRESS=1
All debug_assert() checks-D ASSERT=allIndependent of -g and -O

A typical debug configuration combines flags explicitly: mojo -g -O0 -D ASSERT=all app.mojo. A typical release build needs none: plain mojo app.mojo already uses -O3, emits no debug info, and disables sanitizers.

debug_assert() and -D ASSERT

debug_assert() is a runtime assertion controlled by -D ASSERT — -g and -O don't affect it. Levels: none (off), safe (default — only assertions tagged assert_mode="safe"), all, and warn (run everything, warn instead of aborting). Convention: tag constant-time checks (bounds, comparisons) as safe; leave expensive traversals and allocations untagged:

# Runs under default -D ASSERT=safe:
debug_assert[assert_mode="safe"](
    n >= 0,
    "nth: n must be non-negative",
)

# Untagged — runs only under -D ASSERT=all / warn:
debug_assert(len(data) > 0, "data must not be empty")
from std.sys.compile import OptimizationLevel, DebugLevel

def main():
    comptime if OptimizationLevel.level == 0:
        print("unoptimized build")

    comptime if DebugLevel.level == "full":
        print("source-aware logging enabled")
⚠️ Watch Out:

The plain Bool form of debug_assert() always evaluates the condition, even when assertions are disabled. And don't confuse Mojo's -D ASSERT with the MAX runtime's MODULAR_DEBUG=assert-level=… — separate systems, separately controlled. (debug_assert() is silently disabled on Apple GPU targets.)

10. Mojo Shared Libraries from C/C++

Chapter 11 called C from Mojo; the reverse works too. Compile Mojo into a shared library and call it from any C-ABI host. Mark exported functions with @export and abi("C"):

from max.algorithm import parallelize
from std.runtime import initialize_runtime

@export("parallel_sum")
def parallel_sum(n: Int64) abi("C") -> Int64:
    initialize_runtime()

    var count = Int(n)
    var results = List[Int64](length=count, fill=0)

    @parameter
    def fill(i: Int):
        results[i] = Int64(i)

    parallelize[fill](count)

    var total = Int64(0)
    for r in results:
        total += r
    return total
# Int64 matches C's long long across the ABI
#include <stdio.h>

extern long long parallel_sum(long long n);

int main(void) {
    printf("sum=%lld\n", parallel_sum(1000));
    return 0;
}
mojo build mylib.mojo --emit shared-lib -o libmylib.so
cc main.c -o main -L. -lmylib -Wl,-rpath,'$ORIGIN'
./main
sum=499500
⚠️ initialize_runtime() is mandatory:

When Mojo starts from its own main(), generated startup code initializes the runtime thread pool that parallelize() and TaskGroup depend on. Under a C host, that code never runs — a runtime-dependent exported function segfaults. Either call initialize_runtime() at the top of every exported function (simplest, idempotent, cheap) or export a dedicated mylib_init() and require the host to call it once.

Other differences from a Mojo executable: sys.argv() isn't populated, the crash-stack-trace signal handler isn't installed, and the runtime lives until process exit. On macOS, build a .dylib and run install_name_tool -id @rpath/libmylib.dylib libmylib.dylib before linking.

System requirements recap

  • OS: macOS Sequoia 15+ (Apple silicon M1–M5), Linux with glibc 2.34+ (Ubuntu 22.04 LTS is the tested distribution), or Windows via WSL.
  • CPU: x86-64-v3 (Haswell-class, ~2013 onward) or ARM64 Neoverse N1+; 8 GiB RAM minimum for development.
  • Software: a C compiler on Linux (used as linker); Xcode or Command Line Tools 16+ on macOS.
  • GPU (optional): NVIDIA (driver 580+; B200/H100/A100/RTX series …), AMD ROCm/HIP (MI300X, Radeon RX …), or Apple silicon GPUs — no GPU required to use Mojo.

11. Chapter Summary

  • Modules are single .mojo files of importable API — no main() needed; import via from m import X, import m, or import m as alias (same directory only).
  • Packages are directories with a required __init__.mojo; import as from mypackage.mymodule import MyPair. __init__ can't run top-level code, but its re-exports (from .mymodule import MyPair) lift members to package scope — the max.algorithm pattern.
  • Precompiled packages: mojo precompile mypackage -o mypack.mojoc — faster loads, non-elaborated and cross-system shareable, but tied to the exact compiler version; renaming requires re-precompiling. Non-identifier names use backtick-escaped imports.
  • Targets: query with --print-effective-target and friends; set with Mojo flags (--target-triple/-cpu/-features/-accelerator) or GCC-style (--march/-mcpu/-mtune) — never mixed. GPUs: --target-accelerator=nvidia:sm_90, amdgpu:gfx942.
  • Cross-compilation works for object/asm/IR emits; linked executables need an external platform linker; cross binaries don't bundle Python/C/Modular runtime libraries.
  • Defines: -Dkey=value read via is_defined[], get_defined_bool/int/string/dtype[] — first-class compile-time parameters, gated with comptime if, guarded with comptime assert.
  • Platform detection: CompilationTarget.is_linux()/is_x86()/has_avx512f()/…; target queries (is_gpu()) differ from host queries (has_accelerator()).
  • Debug vs release: independent axes — -g/-O0/--sanitize=address/-D ASSERT=…; plain mojo app.mojo is already -O3 release. debug_assert() follows -D ASSERT alone; read levels via OptimizationLevel.level/DebugLevel.level.
  • Hosted Mojo: --emit shared-lib + @export … abi("C") + initialize_runtime() puts Mojo kernels inside C/C++ hosts.
