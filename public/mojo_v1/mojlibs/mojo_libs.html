Introduction

Mojo is a systems language, but the best Mojo libraries are not just fast. They are predictable, well-typed, and easy to trace. This tutorial treats library design as a craft: small public surfaces, honest contracts, and code that is easy to read when it is deployed in real work.

Scope. We build a single, self-contained book around seven package sketches: geomatics, statistics, operations research, finance, data analytics, mathematics and physics.

Version note. The examples in this document target Mojo 1.1 syntax. No Mojo toolchain is available on this machine, so runtime transcripts are not claimed here. The arithmetic is deliberate and checkable.

A library is a promise

In Mojo, a library is usually a package directory with a public __init__.mojo file and a small set of modules that expose a coherent API. The value of a library is not the number of functions. It is the clarity of the contract: what input does it accept, what units are assumed, what errors are raised, and what numerical defaults it chooses.

Before writing code, decide what the package is for and which assumptions are non-negotiable. In surveying, the library must carry angle units explicitly. In statistics, the library must distinguish sample and population variance. In finance, the library must distinguish arithmetic from log returns. Those are not incidental details; they are the reason the library exists.

A minimal package shape

Here is the package shape used throughout the tutorial.

That public API is intentionally small. It tells callers what is supported and it gives maintainers a place to enforce stable semantics. A large, noisy API is often a sign that the library is still deciding what it is.

Three layers: app, package, module

Mojo code is easiest to reason about when you keep the layers distinct. The application is where you collect inputs, the package is the contract, and the module is the implementation.

  • Application: a small program that reads input, calls the library, and prints a result.
  • Package: a directory containing one public __init__.mojo and a small set of modules.
  • Module: a file that contains the actual algorithmic code.

Package layout

mojo_core/ |-- matrix.mojo |-- numeric.mojo |-- random.mojo `-- vec.mojo

The package root is not a dumping ground. It is the public surface. The modules underneath implement the details. Good package design keeps the import path honest: callers choose a capability, not a random file.

That is why every package in this tutorial exports a predictable API from its __init__.mojo and keeps concrete logic in focused modules such as descriptive.mojo, risk.mojo, or lp.mojo.

The conventions that make the code readable

Mojo 1.1 uses a small, direct syntax. In this tutorial we treat the following as the baseline:

  • def defines a function.
  • var is the mutating variable declaration; comptime is used for compile-time values.
  • Argument conventions are written as mut, var, ref, out, and deinit where needed.
  • Libraries expose a stable interface through package re-exports, not by leaking internal implementation details.

Example function

Good Mojo library code is not clever for its own sake. It is explicit about inputs, output units, and failure modes. That keeps the API honest and makes testing much simpler.

Anatomy of a package

The package directory is part of the public contract. A package should be easier to navigate by reading its tree than by reading its code by accident.

mstats/ |-- descriptive.mojo |-- probability.mojo `-- relationship.mojo

Public API and implementation split

Notice how the package root is just re-exports. That is the right separation of concerns: the package tells the story, while the modules own the details.

Designing the public API

A public API is not a place to dump everything you know. It is a place to communicate clear assumptions. The best library APIs are narrow, explicit, and hard to misuse.

  • Semantic names. Prefer normal_cdf over a vague cdf.
  • Unit-bearing names. Prefer bearing_deg over an ambiguous bearing.
  • Violations raise. Empty data, mismatched lengths, and invalid probabilities should fail loudly.

A stable domain surface

These domain packages are intentionally small. The goal is not to mimic a sprawling ecosystem. It is to give each domain a thoughtful, trustworthy core.

Build, run, test, refine

Mojo's workflow is simple. You build modules, run examples, and keep tests close to the code to make regressions impossible to ignore.

The important habit is not the command itself. It is the loop: write the smallest API that expresses the domain, run a focused example, and test the edge conditions that would silently produce wrong numbers.

4. Financial management and risk

Finance code is easy to get subtly wrong because return conventions are messy. A monthly return, a log return, and a simple gross return are not interchangeable. The package makes that distinction part of the API.

Return conventions and risk

5. Data analytics

Data analytics packages make the library's data model explicit. Missing values, irregular time series, and rolling windows are rarely one-off problems; they are part of the domain contract.

Good data libraries are careful about completeness. They do not pretend an observed value is a true value just because the array is dense enough.

6. Mathematics

Mathematics libraries often become the substrate for everything else. They should be dependable, numerically honest, and careful about what conditions a solver requires.

Packaging and publishing

Once the API is stable, packaging is mostly a matter of making the structure obvious. The language manual describes packaging as a directory plus a package surface, and that is exactly how the tutorial organizes each library.

In a real Mojo environment, the package is then built or precompiled for distribution in the target environment. The important design point is not the packaging format alone; it is that the public surface can survive being moved, cached, or re-exported without unexpected internal coupling.

Python interop and trust boundaries

Once a Mojo package is useful, the next question is usually whether it can be consumed from Python without leaking implementation details. That is a design decision, not a packaging trick.

Keep the Python-facing surface small. A Python caller should be able to import a package, call a few stable functions, and treat the result as data. They should not need to understand your internal module graph or your internal mutable state.

A good interop pattern

Expose domain-specific values, not private helper objects. The public API should be simpler than the implementation.

The point is not merely that Python can call Mojo. It is that your boundary is explicitly chosen. The library still owns the semantics, while the external caller gets a predictable, documented contract.

Advanced patterns: traits, comptime and safety

Once a library is trusted, the next level is to make that trust systematic. That means using comptime values where the compiler can enforce invariants and using traits to communicate capabilities rather than scattering type checks through the code.

  • comptime values encode invariant configuration.
  • traits state what a type can do without requiring runtime branch logic.
  • error contracts are clearer than silent coercions.

A simple safety pattern

That rule is small but important. It prevents meaningless results from spreading through the program and gives downstream callers a precision target when they need to handle the failure.

Professor's rules of thumb

Production libraries are judged by how they fail when the input is bad. A library that looks correct on the happy path but silently misbehaves at the boundary is not trustworthy.

  1. Make every domain assumption explicit: units, variance convention, return type, error policy.
  2. Keep the public surface smaller than the implementation. The package should communicate confidence.
  3. Write tests that fail on edge cases, not just on the normal path.
  4. Prefer small, honest APIs over heavy reflection or hidden magic.
  5. Document the defaults and make them easy to override.

The best library is one that makes its users feel safe enough to operate on real data without losing the ability to reason about what the code is doing.

Exercises

If you want to learn this material by doing it, start with the following tasks.

  • Add a trimmed_mean helper to the statistics package and test it on symmetric and skewed data.
  • Add a traverse validation report in geomatics that rejects closure errors above tolerance.
  • Extend the finance package with a value_at_risk function that matches a specified confidence level.
  • Implement a simple queueing or scheduling model in the operations research package.
  • Build a first-order time-series smoother in the analytics package and test it against a known trend line.

Each of these is a library-sized problem, but each one is also a good way to learn how a small API grows into a real domain tool.

Conclusion

Good Mojo libraries are not built by accumulating features. They are built by making the domain assumptions explicit and by giving the caller a contract that can be trusted under ordinary and abnormal conditions.

The arc of this book has been simple and deliberate: start with the package model, define the rules of the language, design a narrow API, build a workflow, and then see the same principles applied across seven domains. That progression matters. A library is strongest when the design choices around units, probability conventions, risk definitions, and failure cases are visible rather than implied.

The best next step is not to build an enormous codebase. It is to pick one domain and make one package a little more complete than the sketch in this document. Use the package layout here as a template, then refine the API around the actual semantics you need. The right library is not the one with the largest number of functions. It is the one whose contract a domain expert can read and trust.

Final reminder. The examples in this tutorial follow Mojo 1.1 conventions as documented in the source-of-truth manual. They are intentionally explicit about naming, return conventions, and error handling so the code remains readable and teachable.
