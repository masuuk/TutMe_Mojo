Professor's rules of thumb

Production libraries are judged by how they fail when the input is bad. A library that looks correct on the happy path but silently misbehaves at the boundary is not trustworthy.

  1. Make every domain assumption explicit: units, variance convention, return type, error policy.
  2. Keep the public surface smaller than the implementation. The package should communicate confidence.
  3. Write tests that fail on edge cases, not just on the normal path.
  4. Prefer small, honest APIs over heavy reflection or hidden magic.
  5. Document the defaults and make them easy to override.

The best library is one that makes its users feel safe enough to operate on real data without losing the ability to reason about what the code is doing.
