Chapter 8

Metaprogramming

Parameters, constraints, compile-time execution, lambdas, closures, and reflection — writing code that writes code.

1. Parameters vs. Arguments

A parameter is a compile-time input to a struct or function; an argument is a run-time value. Mojo makes this distinction visible in syntax: square brackets [] for parameters, parentheses () for arguments:

def multiplier[factor: Int](x: Int) -> Int:
    return x * factor

def main():
    comptime times_ten = multiplier[10]   # partially applied at compile time
    var x10 = times_ten(3)
    print(x10)
30

Parameters can accept ordinary values (factor: Int, value-parameterized) or types (T: AnyType, type-parameterized). When you call a parameterized function, the compiler resolves the parameter values during compilation and creates a concrete, specialized version for each unique combination — this is how Mojo delivers both generic-looking code and zero-overhead machine code.

If the compiler can't resolve every parameter value to a compile-time constant, compilation fails. There are no run-time "generics":

def repeat[count: Int](msg: String):
    comptime for i in range(count):   # fully unrolled at compile time
        print(msg)

def main():
    repeat[3]("Hello")
Hello
Hello
Hello
💡 Key Insight:

comptime for requires loop limits known at compile time — which is exactly what a value parameter guarantees. After resolution, repeat[3] is equivalent to three unrolled print calls in the compiled program.

Reading a parameter list

Parameter lists support a few special separators, mirroring argument-list rules:

SyntaxMeaning
//Everything before it is an infer-only parameter — inferred at the call site, never written explicitly
/Parameters before it are positional-only
*Parameters after it are keyword-only
*TypesVariadic parameter (pack of compile-time values); later params become keyword-only
= valueOptional parameter with a default

2. Constraining Parameters

Type parameters usually carry a trait constraint, written after the colon. This tells callers what the parameter must support — and tells you what you're allowed to do with values of that type inside the body:

def repeat[
    MsgType: Writable,   // trait constraint...
    //,                  // ...and infer-only
    count: Int
](msg: MsgType):
    comptime for _ in range(count):
        print(msg)

def main():
    repeat[2](42)   # MsgType inferred from the argument
42
42

The // marks MsgType as infer-only: the compiler deduces it from msg, so the caller only writes repeat[2](42). Infer-only parameters keep signatures readable when the type is obvious from the arguments.

Choose minimal constraints

Constrain each parameter only to the traits your body actually uses. Over-constraining rejects valid calls; under-constraining produces confusing "underspecified" errors deep inside the body:

# Good: requires only what's used
def all_equal[T: Equatable](list: List[T]) -> Bool:
    for item in list[:]:
        if item != list[0]:
            return False
    return True
# With T: AnyType instead, the == above fails to compile:
# ERROR: invalid comparison: value does not conform to trait 'Equatable'
📌 Tip:

Start unconstrained or with AnyType, then add the narrowest trait that fixes each compile error. The constraint set documents exactly which capabilities your algorithm needs.

3. Parameterized Structs & Self.T

Structs take parameters the same way functions do. Inside the body, reference a parameter with dot syntax on Self — Self.T means "the T of this particular instance":

struct Pair[T: Movable](Writable):
    var first: Self.T
    var second: Self.T

    def __init__(out self, first: Self.T, second: Self.T):
        self.first = first^
        self.second = second^

    def write_to[W: Writer](self, mut writer: W):
        writer.write("(", self.first, ", ", self.second, ")")

def main():
    var p = Pair(1, 2)   # Pair[Int] inferred from the arguments
    print(p)
(1, 2)

Self stands for the fully-concrete struct type — inside Pair[Int], Self is exactly Pair[Int]. You can also access parameters from outside via dot syntax: Pair[Int].T or on an instance like x.dtype.

comptime members

Structs and traits can declare compile-time members: constants derived from parameters, associated types, or type-safe enumerations. Parameters are supplied by the user; comptime members are computed or declared:

struct Circle[radius: Float64]:
    comptime pi = 3.14159265359
    comptime circumference = 2 * Self.pi * Self.radius

def main():
    print(Circle[1.0].circumference)
6.28318530718

Two common patterns: associated types (like List[T]'s IteratorType naming what iteration yields) and enumerations (comptime constants holding instances of the struct itself — how DType.float32 works). A comptime member without an initializer is a required value: conforming types must supply it.

4. Constraints with where

Trait constraints limit types; where clauses constrain values and combinations that traits can't express. A where clause is a precondition for calling a function or instantiating a struct:

# Constrain parameter values...
def pow2[n: Int]() -> Int where n >= 0: ...

# ...multiple parameters at once...
def subspan[start: Int, end: Int](self) -> Self where end > start: ...

# ...or gate a method on the element type's traits.
# The struct works for all T; sorting only where sortable:
def sort(self) where conforms_to(Self.T, Comparable): ...
# Conditional trait conformance:
# MyContainer is Copyable only when its elements are.
struct MyContainer[T: AnyType](
    Copyable where conforms_to(T, Copyable)
): ...

The knowledge system

The compiler doesn't evaluate propositions like size > 0 mathematically — it tracks them symbolically, per scope. Each scope accumulates a set of known-true propositions ("knowledge"), and a call compiles only if its requirements are covered by known facts at the call site. Knowledge enters four ways:

  1. Constraints declared on the enclosing struct (instances can only exist if true).
  2. Constraints declared on the enclosing function (callers must prove them).
  3. Inside a comptime if — the condition is known within the body.
  4. After a comptime assert — compilation fails if it's false, so code after it may assume it.
def print_first[size: Int](l: Array[Int, size]) where size >= 1: ...

def print_first_two[size: Int](l: Array[Int, size]) where size >= 2:
    # Knowing `size >= 2` doesn't auto-prove the callee's exact proposition,
    # so introduce evidence explicitly:
    comptime assert size >= 1   # add `size >= 1` to the knowledge base
    print_first[size](l)         # now compiles
# Without the comptime assert:
# error: invalid call to 'print_first': lacking evidence to prove correctness

A few conveniences apply: A and B in scope satisfies a requirement of A alone, expressions are canonicalized (x > 0 equals x >= 1), and function calls in propositions are opaque — two identical calls match, but nothing else proves them. Don't rely on cleverness: introduce evidence explicitly with comptime assert.

5. Compile-Time Execution (comptime)

The comptime keyword marks code that runs while compiling. You've seen comptime for; it also declares compile-time constants and gates code with comptime if:

def describe[size: Int]():
    comptime label = "big"   # computed at compile time
    comptime if size >= 4:    # only this branch is instantiated
        print(label, "buffer:", size)

def main():
    describe[16]()
    describe[2]()   # prints nothing — branch not instantiated
big buffer: 16

Inside a comptime if, the condition becomes known knowledge (see the previous section), so nested constraints can be proven. A comptime for unrolls its body; both require everything they test to be resolvable at compile time.

Materialization

Moving a compile-time value into a run-time variable is called materialization. Trivially copyable values (Int, Bool, SIMD) materialize implicitly. Values that allocate — like List or Dict — must be materialized explicitly, because the compiler wants you to control where heap allocation happens:

def lookup_fn(count: Int):
    comptime list_of_values = [1, 3, 5, 7]
    for i in range(count):
        var lookup = list_of_values[i]
        # ERROR: cannot materialize comptime value of type 'List[Int]'
        # to runtime because it is not 'ImplicitlyCopyable'
def lookup_fn(count: Int):
    comptime list_of_values = [1, 3, 5, 7]
    var list = materialize[list_of_values]()   # allocate once, outside the loop
    for i in range(count):
        var lookup = list[i]
        process(lookup)

Materializing inside the loop would create and destroy the list on every iteration. The explicit requirement puts you in control of when resources are allocated.

Two more tools

  • Sub-expressions: var y = x * comptime (calculate_something()) evaluates just the parenthesized expression at compile time — no named temporary needed.
  • Static globals: Mojo has no general global static data yet, but global_constant[numbers]() copies a comptime value into static constant storage once; bind the result with ref lookup_table = ... (a var would trigger an illegal copy). Works for pointer-free values like stack-allocated Array.

6. Lambda Expressions

A lambda is a small anonymous function written exactly where it's used. The body is always a single expression:

var inc = lambda (x: Int) -> Int: x + 1

print(inc(4))   # 5
5

Lambdas shine with higher-order functions, which separate an algorithm from caller-supplied logic. Function-typed arguments use infer-only typing (F: def(T) -> U, //) so the compiler deduces the exact callable type:

def bubble_sort[
    T: ImplicitlyCopyable & Deinitable,
    F: def(T, T) -> Bool,   //
](compare_fn: F, mut values: List[T]):
    for end in reversed(range(len(values))):
        for i in range(end):
            if compare_fn(values[i], values[i + 1]):
                values[i], values[i + 1] = values[i + 1], values[i]

def main():
    var values: List[Int] = [3, 1, 4, 1, 5, 9]
    bubble_sort(lambda (a: Int, b: Int) -> Bool: a > b, values)
    print(values.__str__())
[1, 1, 3, 4, 5, 9]

Swap the comparison for a < b and the same algorithm sorts descending — the caller owns the policy, the function owns the mechanism.

Thin lambdas vs. closures

A lambda that captures nothing is a thin lambda — just an inline function. Thin lambdas can be passed as compile-time parameters, which lets the compiler inline them completely. A lambda that captures surrounding state is a closure; closures work only as run-time arguments:

def inplace_transform[
    T: ImplicitlyCopyable & Deinitable,
    //, f: def(T) thin -> T   # compile-time function pointer
](mut list: List[T]):
    for index in range(len(list)):
        list[index] = f(list[index])

def main():
    var numbers: List[Int] = [1, 2, 3, 4, 5]
    inplace_transform[lambda (x: Int) -> Int: x * 2](numbers)
    print(numbers.__str__())

    # var factor = 3
    # inplace_transform[lambda (x: Int): x ** factor](numbers)
    # ERROR: capturing 'factor' makes this a closure — not allowed as a parameter
[2, 4, 6, 8, 10]
📌 Tip:

The same capturing lambda compiles fine when passed as a run-time argument. Rule of thumb: compile-time parameter → must be thin; run-time argument → closures welcome.

7. Closures & Capture Conventions

A closure retrieves values from its defining scope instead of receiving them as arguments. Each captured name gets an explicit convention in braces after the parameter list — mirroring the argument conventions from Chapter 7:

CaptureMeaning
{imm name}Read-only reference (the default when no list is given)
{mut name}Mutable reference — changes persist in the outer scope
{var name}Copy taken at definition time (snapshot)
{var name^}Move capture — the closure takes ownership
{var^}Makes the whole closure copyable/movable
{ref name}Shares the origin's existing mutability — advanced, for generic code
{}Empty list — body may only use its own arguments
 
def main():
    var greeting = "Hello"
    var calls = 0

    def greeter(name: String) {imm greeting, mut calls}:
        calls += 1
        print(greeting + ", " + name + "!")

    greeter("Alice")
    greeter("Bob")
    print(calls)
Hello, Alice!
Hello, Bob!
2

Entries are independent: {mut count, var label} mixes a mutable reference with a definition-time snapshot. You may include at most one implicit entry — {mut, var z} means "everything else by mut, except z which is copied."

The standard library builds on closures to separate what runs from how it's dispatched:

from max.algorithm import parallelize

def main():
    var results = List[Int](length=8, fill=0)

    def work(i: Int) {mut results}:
        results[i] = i * i

    parallelize(work, 8)
    print(results.__str__())
[0, 1, 4, 9, 16, 25, 36, 49]

You supply the per-element logic; the library supplies threads, vectorization, or hardware dispatch.

8. Reflection

Reflection lets code inspect its own structure at compile time — enabling automatic == for structs, serialization, diffing, and richer errors, all with zero runtime cost. The reflect[T] alias resolves to a handle with static queries:

def show_type[T: AnyType]():
    comptime type_name = reflect[T].name()
    comptime field_count = reflect[T].field_count()
    comptime field_names = reflect[T].field_names()
    comptime field_types = reflect[T].field_types()

    print("struct", type_name)
    comptime for idx in range(field_count):
        comptime field_type = reflect[field_types[idx]].name()
        var intro = "├──" if idx < (field_count - 1) else "└──"
        print(intro, " var ", field_names[idx], ": ", field_type)

@fieldwise_init
struct MyStruct:
    var x: String
    var y: Optional[Int]

def main():
    show_type[MyStruct]()
struct test.MyStruct
├──  var  x: String
└──  var  y: std.collections.optional.Optional[Int]
APIReturns
reflect[T].name()Fully qualified compiler-resolved name (use base_name() for just "List")
reflect[T].field_count()Number of fields
reflect[T].field_names()Tuple of field names (iterate by index when T is parameterized)
reflect[T].field_types()Tuple of field types
reflect[T].field["host"]One field by name (concrete types only)
reflect[T].field_offset[i]()Byte offset incl. alignment padding — C interop & zero-copy layouts
conforms_to(T, Trait)Compile-time trait check — pair with comptime if

Reflection is compile-time only: the comptime for above unrolls before the program runs. Combined with traits it becomes powerful — a trait's provided method can use reflect[Self] so every conforming struct inherits behavior written once (this is how conforming to Equatable gives you free field-wise ==). Related utilities: type_of(x) feeds an expression's type into parameter positions, and origin_of(x) threads a reference's lifetime through signatures.

⚠️ Heads up:

Mojo reflection is newly introduced and currently incomplete — some capabilities are limited or unstable and may change as the feature matures.

Pulling it together

This function diffs two values of any type, using nearly every tool from this chapter at once — parameters, constraints, comptime if/for, reflection, and conforms_to:

def diff_fields[T: AnyType](a: T, b: T) -> List[String]:
    comptime names = reflect[T].field_names()
    comptime types = reflect[T].field_types()
    var diffs = List[String]()

    comptime for idx in range(reflect[T].field_count()):
        comptime if conforms_to(types[idx], Equatable):
            ref a_val = reflect[T].field_ref[idx](a)
            ref b_val = reflect[T].field_ref[idx](b)
            if a_val != b_val:
                diffs.append(String(comptime (names[idx])))
    return diffs^

@fieldwise_init
struct Config(Equatable):
    var host: String
    var port: Int
    var verbose: Bool

def main():
    var old = Config("localhost", 8080, False)
    var new = Config("localhost", 9090, True)
    for name in diff_fields(old, new):
        print("changed:", name)
changed: port
changed: verbose

9. Chapter Summary

  • Parameters are compile-time inputs in []; arguments are run-time values in (). Every specialization happens at compilation — nothing is resolved at runtime.
  • Constrain minimally: each type parameter should require only the traits your body uses; infer-only (//) parameters keep call sites clean.
  • Self.T references struct parameters; comptime members hold derived constants, associated types, and enum-style values.
  • where clauses constrain values, gate methods conditionally, and enable conditional trait conformance. The constraint system reasons symbolically — prove requirements explicitly with comptime assert.
  • comptime runs code during compilation: constants, comptime if/for, sub-expressions, and explicit materialize[]() for allocating types.
  • Lambdas are one-expression anonymous functions. Thin lambdas pass as compile-time parameters; closures capture state and work as run-time arguments.
  • Capture conventions — {imm}, {mut}, {var}, move captures, copyable closures — mirror argument conventions and make data flow through closures explicit.
  • Reflection inspects types at compile time via reflect[T] and conforms_to, powering zero-cost generic behavior.

Metaprogramming is Mojo's defining feature: the same language expresses run-time algorithms and the code generation that makes them fast. Next, we leave the language core behind and look at how Mojo interoperates with the Python ecosystem it grew out of.
